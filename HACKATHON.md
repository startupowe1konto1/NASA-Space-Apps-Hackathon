# Hackathon: how we work (framework for a team using Claude Code)

This file goes into an empty repo at the moment the hackathon starts (T0). It describes the process: roles, schedule, repo rules and ready-to-paste prompts for Claude Code. **It contains no solution code.** Every project file (`CLAUDE.md`, CI, app skeleton) is generated by Claude after T0, from this description, so the framework does not break the usual "the whole solution is built during the event" rule.

Source: `startupowe1konto1/hackathon-framework`, written after the Warsaw Open Data Hackathon 2026 (17–18 Oct, 4 people, 4 laptops, 66 PRs in 24 hours). Translated to English and adapted for the **NASA Space Apps Challenge 2026** (14–15 Nov 2026). The lessons from Warsaw are in section 15.

**Time counts from T0.** For this event T0 is **Sat 14 Nov 2026, 11:09 CET**. T+3 means 14:09 Saturday; T−2 means two hours before submission. We run the 24-hour plan from section 5 and keep the time between T+24 and the local event's deadline (Sun 15 Nov) as buffer. Do not change the order of the gates.

---

## 0. How to use it

**Day before (leader, 30 min):**
1. Fill in the event card (section 1). Leave blank what you don't know: Claude fills it from the rulebook at T0.
2. Go through the "Before T0" checklist (section 3) with the whole team.
3. Assign roles (section 4).

**At T0:**
1. The leader creates an empty repo and adds this file and the rules (`context/rules.md`).
2. The leader starts Claude Code in the repo folder and pastes prompt P0 (section 14).
3. Others clone the repo when the leader says so and paste prompt P1 (research).

**Top rule:** when this file and the generated `CLAUDE.md` disagree, `CLAUDE.md` wins, because it describes the actual project. When the plan has several versions, the newest wins and `CLAUDE.md` names it.

## 2. Compliance with the rules

These rules apply unless the event card says otherwise.

1. **Nothing in the solution is made before T0.** Before the start you may create accounts, install tools, read the rules and split roles. You may not write code, process data, or prepare solution texts or slides. The first commit in the repo is dated after T0.
2. **Analyses are dated too.** Calculations that the idea rests on (e.g. "how many people are affected") are done after T0 and saved in the repo, so it is easy to show when they were made.
3. **AI use is recorded from the first hour.** Each person writes their own entries in `docs/ai-usage/O<n>.md`; at the end the leader merges them into `docs/AI_USAGE.md`. Separate files avoid conflicts; a shared table caused them.
4. **Libraries and data have a license that allows commercial use**, and their attributions go into the app footer and the documentation.
5. **Confidential materials are not committed.** Organizer or partner data we have no permission to publish stays outside git (`.gitignore` entry) and is shared inside the team outside GitHub.
6. **Nothing changes after the deadline.** At T−1 we freeze the repo and tag the submitted version (`git tag submission`).
7. **One project name** in the README, presentation, app and the submission page. Decided by T+3.

## 3. Before T0 (no code)

Each person:
- [ ] Own GitHub account. The leader checks each login: `gh api users/<login>`. In Warsaw two logins given in chat were wrong, and one person worked from the leader's account, which bypassed `main` protection.
- [ ] `gh auth login` with `repo` and `workflow` scopes.
- [ ] Claude Code (desktop app or CLI), logged in, permission mode chosen (auto recommended).
- [ ] Node LTS, `uv` (if Python is used), Google Chrome (Playwright has no own Chromium on older macOS).
- [ ] On Windows: `git config --global core.autocrlf false`. Python file writes use `newline="\n"`.
- [ ] Charger. For the night: `caffeinate -i -t 21600` (macOS) or sleep turned off.

Leader also:
- [ ] A hosting account that builds commits from all collaborators. Free Vercel Hobby builds only the account owner's commits. Cloudflare Workers builds all of them.
- [ ] Know which countries the data APIs answer from. In Warsaw the city portal answered only Polish IPs and timed out from Vercel's servers (Frankfurt, Stockholm).
- [ ] A team channel for people (messenger), and the agreement that agents communicate through GitHub (section 10).

## 4. Roles

Team size: 3–5 (Space Apps allows up to 6). Each person is one laptop and one main Claude Code session ("lane coordinator") that launches subagents.

| Role | Who | Responsible for |
|---|---|---|
| **O1: leader and integrator** | startupowe1konto1 | repo, `CLAUDE.md`, CI, `main` protection, app skeleton, contracts (shared types), review of `[contract]` PRs, e2e test on `main` every hour, decisions, submission |
| **O2…O(n−1): feature lanes** | _to fill_ | app modules and their data, each in its own folders |
| **On: infrastructure and pitch** | _to fill_ | hosting test by T+1, deploy, live data or proxy, then pitch script, presentation, screenshots, documentation, demo recording |

Role rules:
- **Split by module, not by skill.** Each module has an owner and its own folders, so there are few conflicts.
- **The pitch does not wait for the night.** Person On starts the script around T+4, once the skeleton runs in production.
- **Absence.** A lane with no activity for 60 min (no commit and no reply on the channel) is taken over by O1. In Warsaw lane O2 was silent for hours and was taken over only when the leader asked.

## 6. T0 prompt and what it generates (O1)

Prompt P0 (section 14) has Claude create in the first 30 minutes:

| File / setting | Why |
|---|---|
| `CLAUDE.md` | repo rules from section 8, filled with this project's names |
| `README.md` (draft) | project name, team and number, challenge, links (empty) |
| `.gitignore`, `.env.example` | secrets and confidential data outside git |
| `.gitattributes` | `* text=auto eol=lf`, so files from Windows don't break validation |
| `.github/workflows/ci.yml` | typecheck, tests, build, data validation on every PR (no `--passWithNoTests` once tests exist) |
| `.github/pull_request_template.md` | `Task: <ID>`, what was done, how it was checked, "Decisions made without humans", "Left for a human" |
| `docs/ai-usage/O1.md` … `O<n>.md` | AI usage log, one file per person |
| `docs/DECISIONS.md` | answers to questions, collected up front |
| `main` protection | required PR and `ci` check, **also for admins**, squash only, delete branches after merge |
| "Allow auto-merge" in the repo | merge after green CI without babysitting |
| Issue "Team board" (pinned) | announcements, blockers, "please rebase" |

Repo settings via `gh` (Claude does it, the leader approves):

```bash
gh repo edit --enable-auto-merge --enable-squash-merge --enable-merge-commit=false --enable-rebase-merge=false --delete-branch-on-merge
gh api -X PUT repos/<owner>/<repo>/branches/main/protection --input protection.json
```

`protection.json`: `required_status_checks` with `contexts: ["ci"]`, `enforce_admins: true`, `required_pull_request_reviews` with `required_approving_review_count: 0`, `restrictions: null`. Temporary file, not committed.

## 7. From idea to plan

**Research (T+0:30–2:00, prompt P1).** Each person takes one question, e.g. "what data is available and does the API work with our key", "what already exists (competition)", "who has the problem and what jobs to be done", "can we compute our differentiator from the data". The result goes to `context/<topic>.md` and the answer to chat. The file is an extra, not a replacement for the answer.

**Idea rejection criteria** are set before research, e.g. "we don't duplicate an existing app", "must work offline", "end users only, no admin panel". In Warsaw two concepts and a city admin panel were dropped only during research.

**Facts first:** before the plan we test the API key on 2–3 datasets, save response samples to `data/samples/`, and get library docs through Context7. Parsers are written against saved samples, not from the model's memory.

**Documents (P2):**
1. `HANDOFF.md`: rules (with section numbers), team decisions, concept, differentiator, data, risks, pitch narrative.
2. `docs/SPEC.md` (skill `superpowers:brainstorming`): goal, scope, stack, architecture, **contracts** (shared types in one file), **owner folders**, error states, tests, submission.
3. `docs/PLAN.md` (skill `superpowers:writing-plans`): tasks with IDs (`O2-A1`, `V3`), each with owner, branch, dependencies, a "Files" section, "Done when", TDD steps. The plan is written in parts and joined, because it is long.
4. **Plan pre-flight:** a subagent reads the plan and returns dependencies and questions with recommended answers. The leader accepts them in bulk. Output: `docs/DECISIONS.md` and `docs/tasks.json` (ID, person, branch, `after`, files, conflicts).
5. **Checking code from the plan:** if the plan contains code (e.g. the contract), the leader compiles it in a temporary worktree before the team builds on it.

**Data proof for the pitch:** the number the narrative rests on is computed by a script in the repo, and a second person checks it independently before it goes into slides. In Warsaw a wrong 69.1% was already in six files before someone questioned it. The correct result was 91.5%.

**Second iteration (T+8):** if the T+7 review changes the concept, write `HANDOFF-v2.md` and `docs/PLAN-v2.md`. `CLAUDE.md` immediately points to the plan in force.

## 8. Repo rules (content for `CLAUDE.md`)

Claude pastes this into `CLAUDE.md` at T0 and fills in the brackets.

```markdown
# Repo rules (read before every change)

- Spec: docs/SPEC.md. Current plan: docs/<PLAN>.md (a newer version wins). Decisions: docs/DECISIONS.md.
- You work on one task from the plan (ID, e.g. O2-A1). PR title starts with the ID.
- You write only in your person's folders (SPEC §<n>). Any other file: a separate small PR titled `[contract] ...`, reviewed by O1.
- Shared types only from <contracts file>. A new dependency only through a [contract] PR.
- Each session works in its own git worktree, never in the main folder while another session runs there.
- Dev server port: O1 5171, O2 5172, O3 5173, O4 5174. e2e tests only on O1's laptop.
- Never: push to main, `--force` without `--with-lease`, `gh pr merge --admin`, `git add -A`, push to someone else's branch.
- Secrets only in .env (local) and hosting variables set via CLI. Never in code, logs, PRs, chat.
- Data only from the allowed sources: <domain list>. Any other server = ask a human.
- Generated files (<e.g. manifest>) are regenerated with a script after a conflict, never merged by hand.
- API parsers are written against a saved sample in data/samples/, not from memory.
- TDD: test → red → code → green. UI tests wait for specific text (waitFor), not just the element.
- Before a PR: git fetch && git rebase origin/main && <typecheck> && <test> && <build>.
- Every screen has states: loading, offline, no data, source error. Never an empty screen.
- English UI text and docs go through the anti-ai-writing skill.
- Answer in chat. A file in the repo is an extra, not a replacement for the answer.
- Get the time with `TZ=Europe/Warsaw date`, don't guess.
```

Plus topic-specific content rules (in Warsaw: "shelter locations according to the fire service", never "bunkers"; we don't announce alarms).

**Branch names:** `o<n>/<id>-<topic>`, e.g. `o2/s1-siren-card`. Taken-over task: `o1/<id>-taken-over`.

**Modules:** each module is one folder with one entry point and a registry that only O1 edits. All known dependencies go into the skeleton at T+3, so nobody outside `[contract]` PRs changes the dependency list.

**The e2e test grows with the project:** the persona-path test has steps for each module and enables them itself once a module stops being a stub (e.g. the stub shows "Under construction."). Demo parameters in the URL (`?offline=1`, `?location=lat,lon`) make the test and the demo the same path.

## 9. Task cycle

1. **Claim.** New branch from `origin/main` in its own worktree, empty commit `claiming <ID> (<name>)`, push and **immediately a draft PR** titled `<ID>: …`. A branch without a PR is not enough: in Warsaw the autopilot did and merged several tasks someone was working on locally.
   ```bash
   git fetch origin && git worktree add ../ws-<id> -b o<n>/<id>-<topic> origin/main
   ```
2. **Implementation.** A subagent gets brief P4: only the files from "Files", TDD, decisions from `DECISIONS.md`, no questions to humans; doubts are settled with the option closest to the plan and described in the PR.
3. **Gate.** `git fetch && git rebase origin/main`, typecheck, tests, build, data validation; e2e when the task changes UI and the e2e port is free.
4. **Review.** A reviewer subagent reads the diff against the spec and for quality (P5). Critical and important comments are fixed by the same implementer, and the reviewer checks only the difference. Approval is a comment `Review: approved @<sha7>`, valid only for that commit.
5. **Merge.** Draft → ready, auto-merge after green `ci`. Without auto-merge:
   ```bash
   gh pr checks <n> --watch --fail-fast --interval 20 && gh pr merge <n> --squash --match-head-commit <sha>
   ```
6. **After merge.** `git worktree remove ../ws-<id>` and a note on the board: "merged <ID>, changed files: …; whoever has them in a PR, rebase".

**Conflict check without checkout:** `git merge-tree --write-tree origin/main origin/<branch>`.
**Rebase:** only on conflict or when merge refuses. A `BEHIND` state alone does not need a rebase.
**Model:** mechanical tasks can run on a cheaper model; the core (contract, main screen, integration) and its review on the strongest. Put the right model's commit footer in the brief so it doesn't need fixing by hand.

## 10. Coordination between laptops

- **The agents' channel is GitHub,** the people's channel is the messenger. A blocker or bug is an issue with one sentence "what to do" plus a PR comment. Announcements go on the team board (pinned issue).
- **Task state comes from GitHub, not memory.** O1 (or the autopilot loop) computes it from PRs and branches: done (PR merged), in progress (open PR or commit younger than 90 min), abandoned, ready to start, waiting. In Warsaw a `state.mjs` script written during the event did this; here Claude writes it at T+3 if the team has more than 15 tasks.
- **Hourly integration:** O1 runs e2e on a fresh `main` in a separate worktree. A red result is rerun at once; two reds in a row become an issue "e2e red on main" and a fixing subagent.
- **No permanently red checks.** A check that is always red gets fixed or disabled in the first hour. In Warsaw the Cloudflare preview was red on every PR for 24 h, so the team learned to ignore red checks.
- **One session = one worktree = one port.** Two sessions in one folder in Warsaw ended with `git checkout main` and a push to `main` that skipped the PR, then a fix through `reflog`.
- **Side sessions** (`start_session`) for work that has its own result: CI diagnosis, QA fixes. Brief: background, task, steps, what not to do (e.g. "no real deploy"), "Done when". A session waiting for data from a human (e.g. a dashboard log) gets stuck, so give that data up front or don't start it.
- **A postponed PR** gets draft status or a "do not merge" label, and its scope goes to `docs/TODO-later.md`. Otherwise someone finds the same bugs again in the morning.

## 11. Autopilot (optional)

A `/loop` in each session that every few minutes reads state from GitHub and takes the next step: claims a ready task, launches a subagent, reviews, merges. In Warsaw this way of working (plan with ready tasks, decisions up front, subagents, review before merge) closed 21 of 21 second-iteration tasks in 2.5 h, with about 30 PRs. The loop itself started later and mostly waited.

Turn it on when:
- the plan has tasks with "Files" and "Done when", and `DECISIONS.md` answers questions up front,
- part of the team is asleep or away,
- everyone claims tasks with a draft PR (section 9, step 1).

Avoid:
- **a 5-minute loop with no events:** in Warsaw almost all of about 15 iterations ended "no change". 15–20 min is better, or triggering on a new PR;
- **merging work someone is doing locally:** claiming the task on GitHub is mandatory;
- **heartbeats in a worktree where an agent works:** an empty commit that keeps a claim alive is made with `git commit-tree` and a ref push, without touching the tree.

The loop instructions are a separate file `docs/AUTOPILOT.md` generated after T+3 (P11): merge conditions in one place, limits (at most 2 tasks per lane at once), takeover thresholds, a "never" list.

## 12. Deploy, pitch, QA, night

### Deploy
- **One hosting, chosen by T+1** after a test from its region (`curl -s -m 20 -o /dev/null -w "%{http_code} %{time_total}s\n" <url>`), not after a deploy. In Warsaw a second hosting added 2.5 h before the deadline cost over an hour.
- **Secrets via CLI, not the dashboard:** `grep '^KEY=' .env | cut -d= -f2- | tr -d '\n' | npx wrangler secret put KEY`. Setting it in the Cloudflare dashboard took about 70 minutes in Warsaw; the CLI did it in a minute.
- **Production from `main` automatically,** PR previews green or disabled (section 10).
- **A short public URL without login** (preview protection off), checked in a private window.
- **Decide about the audience's phones before the pitch:** can the QR-code version store anything (PWA, cache)? In Warsaw the app downloaded 27 MB to each scanning phone and needed a separate "online only" mode.
- **Safari and iPhone checked on day one,** not at submission.

### Pitch
- Pitch lane from T+4: script, jury questions with answers, presentation (HTML works offline and has notes), production screenshots taken by a script.
- **UI quotes in the script are checked with grep in the code** before each rehearsal. In Warsaw the script quoted a button that had been renamed.
- **Demo in a clean browser profile,** with URL parameters instead of clicking. A backup demo recording in case there is no network.
- Slide remote: presentation on arrow keys, phone as a Bluetooth keyboard.
- Space Apps judging happens after the event from the project page, so the submission text, demo video and links matter as much as the live pitch.

### QA and review
- **QA (T+13, P7)** in a separate browser profile, on a separate port and on a frozen commit. QA in a shared browser wiped the leader's data in Warsaw, and testing while code was changing gave stale findings.
- **QA report:** issues from most severe, each with steps, expected / actual, cause `file:line`, screenshot; a separate "What works" section. Fix what shows in the demo right away; hand the rest to a side session.
- **Review (T+19, P8):** 4–5 read-only reviewers split by area (skeleton and offline, each module, server and CI, texts and docs). The leader confirms every finding and splits fixes into PRs by folder owner.
- After testing, leave the preview in production state (no `?offline=1`), so it doesn't trigger a false alarm.

### Night
- All features done by T+13. After midnight bugs multiply, so only fixes after that.
- Sleep in 2.5 h shifts, one person on duty for `main`. Laptops on power, lid open, `caffeinate` running.

## 13. Submission checklist (T+22)

- [ ] Repo has the visibility the rules require (public for Space Apps), link opens in a private window.
- [ ] README: project name, team and number, challenge, presentation link, app links, how to run, tests, folder map.
- [ ] Presentation in the repo, named per the event card pattern.
- [ ] `docs/DOCUMENTATION.md`: data used (list of NASA / partner datasets), assumptions and limits, frameworks and tools, attributions. No placeholders (`grep -rn "TO FILL\|TODO" docs README.md`).
- [ ] `docs/AI_USAGE.md` merged from the per-person files: tools, what for, what humans checked, what AI did badly. Its summary goes into the Space Apps submission (required).
- [ ] One project name everywhere.
- [ ] No secrets in history: `git log -p --all | grep -cF -- "<key>"` gives 0, and `trufflehog git file://. --no-update` finds nothing.
- [ ] Zero open PRs: unmerged ones are closed and their scope is in `docs/TODO-later.md`.
- [ ] Production runs at a public URL; QR code read with a phone and labeled with the URL.
- [ ] e2e green on `main`, CI green.
- [ ] `git tag submission && git push origin submission`, project submitted on the team page, confirmation saved.
- [ ] Repo frozen at least 45 min before the deadline.

## 15. Lessons from Warsaw 2026 (where the rules came from)

| What happened | Cost | Rule in this file |
|---|---|---|
| Research with two changes of direction took 2.5 h | first code at T+3:47 | research capped at 90 min, rejection criteria up front (§5, §7) |
| Answers ended up in files, not in chat | "where are the answers?" | answer in chat, file as an extra (§8) |
| Hosting changed three times (Vercel → Pages → Worker) | PR #1 reworked, about 70 min in the dashboard | hosting chosen by T+1, secrets via CLI (§3, §12) |
| `main` protection turned on at T+5:30, one person on the leader's account | admin could push to `main` skipping PRs, and it happened once | protection at T+0:30 with `enforce_admins`, everyone on their own account (§3, §6) |
| Cloudflare preview red on every PR for 24 h | red checks ignored, no previews | no permanently red checks (§10) |
| No auto-merge in the repo | manual CI babysitting | auto-merge at T0 (§6) |
| The pitch's main number computed wrong | fixes in six files | independent check of numbers before slides (§7) |
| Conflicts in a shared `AI_USAGE.md` table | manual merging | one file per person (§2) |
| Windows CRLF broke package validation | O2 integration delayed | `.gitattributes` with LF at T0 (§3, §6) |
| Handoff v3 without an execution plan | 30 min writing a plan, contract after deadline | plan with IDs, "Files" and "Done when"; `CLAUDE.md` names the current plan (§7) |
| Autopilot merged tasks someone was working on locally | double work | claim with a draft PR from minute one (§9) |
| 5-minute loop | about 15 empty iterations | longer interval or event trigger (§11) |
| Overpass outage, data came from a mail.ru server | human intervention, PR #51 | allowed data sources list in `CLAUDE.md` (§8) |
| Lane O2 silent for hours | takeover only on request | takeover after 60 min of silence (§4) |
| QA in a shared browser, port collisions 5173/4173/4174 | false alarms, wiped data | separate profile, port per person, frozen commit (§8, §12) |
| Two sessions in one folder | push to `main`, fix through `reflog` | one session = one worktree (§10) |
